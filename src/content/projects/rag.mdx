## Context and constraints

Every ad-hoc question about the business — how did this category do last month, which stores
are carrying dead stock, what happened to margin in that line — arrived as a message to the one
person who could write the query. That is a bottleneck for management and a waste of an
analyst, and it is the textbook case for putting a language model in front of the warehouse.

It is also the textbook case for getting it badly wrong. A model that answers "roughly 340
million" when the real figure is 290 million has not made an error a user can detect. It has
produced something that looks exactly like an answer, in a channel where people make decisions.
For an assistant that management will trust by default, a confidently wrong number is worse
than no assistant at all — so the design constraint came before the design: **no figure the
user sees is generated by the language model.** Every number comes from a query that ran.

One more constraint shaped the build. This assistant is a pure consumer of a data warehouse
that a sibling project already models and documents. It does not re-derive domain knowledge
inside the bot. If the definition of a metric is wrong, it is wrong in one place, and that
place is the warehouse.

## Architecture decisions

The system has **two answer paths, and the split is the architecture.**

<Diagram spec={diagrams.rag} />

The **certified path** handles the questions that get asked constantly. These have closed SQL
recipes written and reviewed ahead of time, and a deterministic composer assembles the metrics
in code. No model writes anything here. For these questions the assistant is a natural-language
front end to a set of known-correct queries, which is exactly what it should be.

The **dynamic path** takes everything else. Here a model does write SQL — and then that SQL
goes through lexical validation, a dry-run execution, and a bounded retry before it is allowed
near real data. The model is treated as an untrusted contributor whose work gets reviewed, not
as an oracle.

The measurement that keeps this honest is the **share of questions falling into each path**,
tracked as a health signal and deliberately *not* as a target. The moment "get more traffic on
the certified path" becomes a goal, the incentive is to widen recipes until they answer
questions they were not written for, which is how you re-introduce the wrong answer through
the door marked safe. The ratio is a thermometer. Thermometers stop being useful when you start
optimising them.

Model and provider selection followed the same discipline in a smaller way: the switching
criteria — accuracy and latency thresholds, plus a scheduled quarterly review — were written
down *before* the measurements were taken. Choosing thresholds after seeing the results is how
you end up justifying the provider you already liked.

## The hard part

The interesting failure here is one of mine.

Model calls cost money, and this runs on my own judgment about spend, so I built a guardrail: a
hook that intercepts shell commands and blocks the ones that would call a paid provider. It
worked in testing. Then I audited it adversarially — actively trying to get a billable call
past it rather than confirming that the happy path was blocked — and the great majority of ways
to invoke a command went straight through. Aliases. A different quoting style. Environment
variables. A wrapper script. Any of it.

The lesson was not "the pattern list needed more patterns." It was that **the approach could not
work**, and no amount of iteration would have fixed it. A shell is a complete programming
language. Deciding by text inspection whether an arbitrary shell command will eventually spend
money is not a hard problem, it is the halting problem wearing a hat. A denylist over a Turing-
complete surface is theatre.

So the control moved. Instead of trying to forbid the many ways of reaching the paid provider,
the code has exactly **one entry point** to it — and an automated test fails the build if a
second one appears. The guarantee is no longer "we thought of every invocation," it is "there
is one door, and CI notices if someone cuts another." That is a property you can actually hold.

The generalisable version, which is why this is the story I lead with on this project: when a
control is placed where it is convenient to enforce rather than where the thing it controls
actually happens, it will look like it works right up until someone checks. And in AI systems
the controls are usually placed at the prompt — the most convenient and least enforceable
surface there is.

## Trade-offs

**Per-call confirmation is paused, on purpose.** There is a hook that asks before each model
call. While the provider's free tier cannot generate a real charge, that prompt is friction
with nothing behind it, and friction with nothing behind it trains you to click through — which
is precisely the reflex you do not want in place when the account does start billing. It comes
back on with paid usage. Keeping a control switched on for appearances is worse than switching
it off deliberately and writing down why.

**The certified path costs maintenance.** Closed recipes have to be written and kept in step
with the warehouse. That is real ongoing work, accepted because the alternative — one dynamic
path for everything — puts the highest-traffic, highest-trust questions on the least
deterministic machinery.

**Open-weight models over frontier models.** Groq's open-weight models are fast and cheap
enough to make the dynamic path viable at all, at some cost in SQL-writing quality against the
best available models. The validation-and-dry-run layer is what makes that trade acceptable:
the floor is set by the checks, not by the model.

## What the numbers are

The core carries no dependencies beyond the standard library — a deliberately small failure
surface for something that sits between management and the warehouse. Dozens of automated tests
cover the chain from SQL validation to the spend guardrails themselves. The system is in active
construction; the guardrails were built first, before any of the conversational product, which
is the ordering I would defend as the point of the project.

Business figures are given as ranges deliberately: the company is named, the exact numbers
are not mine to publish.
